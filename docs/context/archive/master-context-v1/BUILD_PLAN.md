# SoloUnicorn delivery plan

This plan scopes a playable product without requiring the full catalogue before the causal loop works. Task IDs, dependencies and model tiers are in `data/delivery_plan.json`. The current engine package is a reference contract, not a claim that any milestone is implemented in the live repository.

## Milestones

| Milestone | Build | Evidence to call it complete |
|---|---|---|
| M0 — Adopt contracts | Inspect live checkout, merge context bridge, map current code and define state/action/effect/save interfaces | Actual commit/dirty baseline, file gap map, discovered commands, engine profile and unresolved scope |
| M1 — First founder quarter | Deterministic clock/attention, Demand → Product → Monetisation, service billing/collection, one Retention threat, one Expansion path, basic Ops obligation, cash upgrade, local save, responsive representative gestures | Exact ARR/cash bridge, replay parity, continuous-time behavior, failure/payment fixtures, one-active-function proof and mobile/desktop interaction evidence |
| M2 — Leverage and pressure | Visible agent work, Craft/Scale/Automate/Luck slice, recurring upkeep, accumulated strain, rot, rework, Operations allocation and sustainable/overextended configurations | Founder/agent resolver parity, finite input accounting, overloaded failure attribution, measurable attention relief, two distinct build choices |
| M3 — Replayable company | Full six-function causal loop, debt, VC mandate/dilution, progressive HUD, contextual events, founder history, successful-founder relic handoff and unicorn continuation | Complete/censored run reports, cash/debt/equity reconciliation, first-run/repeat-founder segments, build differences and no unimplemented effects in active pools |
| M4 — Release candidate | Chosen content subset, full art/audio treatment, PWA/offline/update recovery, responsive/accessibility/performance pass and broader balance assessment | Repository gates, declared device evidence, effect/content validation, player sessions and separate owner/human-acceptance status |

## Order of work

Build one thin causal vertical slice first. Do not author all long-term rank slots or relics before six functions, cashflow and attention are playable. Implement agents and Operations together so automation is a real execution path with costs and failure exposure. Implement financing only after service, billing and due-payment order are real. Add generated narrative after authored event envelopes and fallback copy work offline.

The current long-term tree inventory has four axes and four subbranches per axis for each of the six operating functions. Finance is a separate management domain. Its eventual management progression is not enabled by this contract and must not be represented as a seventh reflex loop.

## Evidence discipline

For each change, define the question, profile/content/engine versions, policy or interaction fixture, seed, horizon and stopping rule. Use the real engine, not a disconnected spreadsheet. Classify runs as won, failed or horizon-censored. A sustainable 0%/bootstrap or post-unicorn run can continue; censor it instead of calling it a failure.

Record first-time and successful repeat-founder results separately. Track first-$1B active time, quarters, failure reason, cash shortfall, burn, collections, debt/VC choice, build identity, strain/rot and relic loadout. Successful repeat founders are intended to win more easily; do not merge that result into a single average or “fix” it with hidden difficulty scaling.

Balance validation requires policy sweeps plus human play. A candidate profile passing arithmetic tests is not a balanced release. Measure at least manual, hybrid, automation, Operations, bootstrap, debt, VC and Luck-exposed policies once the full loop exists. Do not invent observed results or claim five viable build families before measuring them.

## Content and relic scope

Every rank, strategy, event and relic references an approved effect ID, explicit values, eligibility, cost, downside, observable change and version. Specific relic effects and stacking rules remain a later evaluation pass. The current interface must preserve persistent successful-founder ownership and report the advantage without normalization.

## Completion report

Every milestone report names included behavior, exact files/versions, commands/tests, seeds and visual evidence. It distinguishes functional prototype, mathematically verified, art-complete, balance-validated, human-playtested and owner-accepted states. Remaining gaps must be named by affected system.
